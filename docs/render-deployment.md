# Render Free deployment: Supabase Staging

This guide prepares a **Docker Web Service** for the existing PHP application.
It does not provision a database, apply migrations, create accounts or deploy anything.
Use the existing **Supabase Staging** project only. Do not copy the local `.env`,
`.env.example` project origin or generated `public/app/core/config.js` into Render;
their project identities have not been verified as Staging.

## Container behavior

- Base image: official `php:8.4-apache-bookworm`, including cURL, mbstring, JSON,
  fileinfo, sessions, OpenSSL and OPcache. The build asserts all these extensions.
- Apache serves only `/var/www/html/public`, listens on `0.0.0.0:$PORT`, defaults to
  port `10000` locally, and runs in the foreground. No Node or Composer installation
  is required in the image; frontend assets are already in `public/`.
- Existing `.htaccess` rules preserve `/`, `/index.html`, `/index.php`,
  `/app/core/config.js`, `/api/`, `/api/index.php` and `/2-engr/index.html`.
  Browser configuration is generated by PHP at request time using Render's runtime
  environment. The generated local JavaScript configuration is excluded from the image.
- `SUPABASE_URL` and `SUPABASE_PUBLISHABLE_KEY` are read by the existing
  `Config::load()`; real environment variables already take precedence over `.env`.
  No Supabase build arguments or embedded credentials are used.
- Render terminates public TLS and redirects public HTTP to HTTPS. With Render's
  automatically injected `RENDER=true`, startup enables an Apache define that sets
  PHP's `HTTPS=on`. This preserves HTTPS origin checks and Secure session cookies.
  Arbitrary forwarding headers cannot enable this mode. Local HTTP runs omit `RENDER`.
  This mode assumes the container is reached through Render's HTTPS edge; do not
  set `RENDER=true` on a directly exposed HTTP server.
- cURL peer and hostname verification in `server/Http.php` remain enabled. The
  image installs CA certificates and configures both PHP/cURL and OpenSSL to use
  `/etc/ssl/certs/ca-certificates.crt`. Do not disable verification to resolve errors.
- Upload limits remain `10M` per file, `16M` per POST/body. Apache has four workers,
  PHP has a `96M` per-request memory limit, and OPcache uses `64M` to fit a small
  instance. Logs go to stdout/stderr; access logs omit query strings and referrers.
- `GET /healthz` checks the PHP version, required extensions and configuration.
  It returns `200 {"status":"ok"}` or `503 {"status":"unavailable"}` without
  exposing configuration or contacting Supabase. `HEAD` is supported; other methods
  return `405`. Docker's health check probes this same endpoint over loopback.
  It is an application readiness check, not proof that Supabase is reachable.
- Existing authentication, bearer forwarding, RLS, permissions, Storage, realtime
  and business workflow code remain unchanged. PHP session metadata is ephemeral;
  verified Supabase bearer tokens still authorize requests.

## Validate locally before approving deployment

Requirements: Docker Engine/Desktop running **Linux containers**. Node 22+ runs the
smoke harness. PHP 8.2+ with the documented extensions is needed only for host tests.

From the repository root:

```sh
npm run check
npm run test:render
npm run test:container
```

On Windows PowerShell use `npm.cmd` if script execution policy blocks `npm`.
The first two commands check source/assets and run loopback-only PHP/TLS fixtures;
they do not run migrations or use a database. Avoid `npm test`, `test:php` and other
database suites under the current no-migrations constraint: some create isolated
databases and apply SQL fixtures even though they do not use live Supabase.

`test:container` builds `mcpa-render-local` and runs it with `--network none`, a
nondefault `PORT=18081`, synthetic keys and a temporary read-only PHP Auth fixture.
It mounts neither `.env` nor the project directory. It checks:

- Apache/PHP entry routes and byte-identical frontend, CSS, JS, modules and images.
- Runtime public configuration, synthetic sign-in, cookie security and bearer forwarding.
- Rejection of missing/privileged bearer tokens, disallowed origins and private routes.
- Required extensions, CA paths, upload limits, HTTP/Docker health checks and
  an actual `0.0.0.0:18081` listening socket.
- Image exclusions and startup rejection of missing Supabase configuration/invalid ports.

The harness removes only its generated containers and temporary fixture directory.
The local image remains for inspection. A missing Docker Engine is a failed check,
not a skipped success. No live Supabase request or database operation is made.

For a later, approved manual Staging check, build with `docker build -t mcpa-render-local .`
and supply only Staging runtime variables with `docker run --env-file <private-staging-env-file>
-e PORT=10000 -p 127.0.0.1:10000:10000 mcpa-render-local` (enter this as one command).
Keep that env file outside the repository and image; set `MCPA_APP_URL` to
`http://127.0.0.1:10000/index.html` and omit `RENDER` for this local HTTP run.
Do not sign in, create accounts, recover passwords or exercise record-changing workflows
until the corresponding Staging actions have been approved.

## Deploy on Render after approval

1. Review the changes and obtain approval to commit/push them, then approval to deploy.
   Render builds committed repository contents; these local edits alone cannot be deployed.
   If an existing Render service watches this repo, turn its Auto-Deploy setting **Off**
   before an approved push to prevent an unintended deployment.
2. In Render choose **New > Web Service**, connect GitHub and select
   `dark-er-00/MCPA2.0`. Use the branch containing the approved changes (normally `main`).
   Choose **Web Service**, not Static Site.
3. Set the following fields:

   | Field | Value |
   | --- | --- |
   | Name | A unique Staging name, for example `mcpa-staging` |
   | Region | Prefer the available region nearest the Supabase Staging project |
   | Branch | `main`, after the approved changes are merged |
   | Language / Runtime | `Docker` |
   | Root Directory | Leave blank (repository root) |
   | Dockerfile Path | `./Dockerfile` |
   | Docker Build Context | `.` if shown |
   | Instance Type | **Free**, not a paid instance |
   | Docker Command | Leave blank; use the Dockerfile CMD |
   | Health Check Path | `/healthz` |
   | Auto-Deploy | **Off** |

   Docker has no separate build command. Do not use `npm start`, `php -S`, a migration
   command, a pre-deploy command or a persistent disk. Leave the provided `PORT`
   environment variable alone; Apache resolves it at every startup.
4. Add these variables in the service's **Environment** settings. Replace every
   placeholder using the Supabase **Staging** dashboard; no real values belong in source:

   | Variable | Value |
   | --- | --- |
   | `SUPABASE_URL` | `https://<STAGING_PROJECT_REF>.supabase.co` |
   | `SUPABASE_PUBLISHABLE_KEY` | The publishable key for that same Staging project; an existing Staging anon key is also supported |
   | `MCPA_APP_URL` | `https://<ACTUAL_RENDER_HOSTNAME>/index.html` |
   | `MCPA_ENABLE_DEVELOPMENT_ACCOUNTS` | `false`, unless an already-enabled Staging feature must be carried over with approval |

   Confirm the project name/ref is Staging before entering values. Use the actual
   assigned Render hostname, not the example service name. Both `/index.html` and
   the API must share this exact origin. The application also works on an approved
   custom HTTPS domain when `MCPA_APP_URL` and allowed Auth URLs use that domain.

   The existing privileged **development-account creation** workflow additionally
   requires a **Staging-only** `MCPA_SUPABASE_SECRET_KEY` if that feature is enabled.
   Existing `SUPABASE_SECRET_KEY`/`SUPABASE_SERVICE_ROLE_KEY` aliases still work.
   Keep these server-only; never use them as the publishable key. Ordinary operations
   do not require them. Setting configuration does not authorize creating accounts.
   Never attach Production environment groups or import the existing local `.env`.
5. After approval for configuration changes, in the **Staging** Supabase dashboard
   open **Authentication > URL Configuration**. Set the Staging Site URL to the
   canonical app login URL and add the exact
   `https://<ACTUAL_RENDER_HOSTNAME>/index.html` redirect URL. Preserve other valid
   Staging redirect entries. This keeps the existing recovery redirect working.
   Do not edit Production Auth settings, schemas, policies, buckets or records.
6. Only after deployment approval, click **Create Web Service**; that action starts
   the first build/deploy. Verify build logs show the extensions check succeeds and
   startup logs show the local preflight and Apache syntax check succeed. Keep
   Auto-Deploy Off for later approval-controlled updates.
7. Open `https://<ACTUAL_RENDER_HOSTNAME>/healthz`, `/index.html`,
   `/2-engr/index.html` and `/app/core/config.js`. Health must be `200`; browser
   configuration must identify only Staging URL/key and contain no server secrets.
   In browser developer tools check CSS/modules/images load and the API is same-origin.
   After approval for a Staging sign-in, use an existing authorized Staging account,
   confirm `MCPA_SESSION` is Secure/HttpOnly/SameSite=Lax and check its existing role
   sees the expected screens. Treat recovery emails, uploads and workflow writes as
   separate actions requiring approval under the current instructions.

## Free-plan behavior

Render Free services sleep after 15 minutes of inactivity and can take about a
minute to wake. The workspace receives 750 free instance hours per month, shared
by its Free services. Bandwidth and build usage limits also apply. Review the
workspace's included usage before deployment; the Free plan is intended for
testing/hobby use, and Render does not recommend it for production applications.

The filesystem is ephemeral: redeploys, restarts and sleep can discard PHP session
metadata. Existing Supabase Auth, PostgreSQL and private Storage remain external;
do not replace them with local files or a Render Postgres database. Free services
have no persistent disks or dashboard/SSH shell. This is why local Docker
validation and `/healthz` are provided.

Official references: [Docker on Render](https://render.com/docs/docker),
[Web Services and port/TLS handling](https://render.com/docs/web-services),
[default Render variables](https://render.com/docs/environment-variables),

and [Supabase redirect URLs](https://supabase.com/docs/guides/auth/redirect-urls).
